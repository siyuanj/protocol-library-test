# Data-management practices in protocol platforms — borrowable ideas for LabRecord

*Synthesis of Scout A (protocol-native journals/platforms) and Scout B (ELN/LIMS software), revised after adversarial verification. Every factual claim is tied to a URL from the two input reports. Cells/claims the scouts could not confirm from a primary source are marked `?` or explicitly flagged unverified. Two low-quality sources cited in the draft (an AI-generated wiki and an SEO blog) have been removed and the claims that rested on them downgraded — see "Evidence quality" at the end.*

> **How to read the field-name strings in the tables below.** Where a cell lists another product's field names, template sections, gadget types, or role names (e.g. protocols.io's gadget list, Nature Protocols' section order, STAR's template chain, eLabFTW's role set), those strings are **cited descriptions of prior art for analysis only**. They are **not** vocabularies to port into LabRecord. Everything we adopt is reimplemented independently on our own canonical JSON with our own field names (see §3).

## 2. Borrowable ideas for LabRecord (ranked)

**What LabRecord already has** (confirmed against `protocol-standard/canonical-schema.json` and `protocol-standard/03-library-version-design.md`, not the draft's self-description):

- Canonical protocol JSON with `metadata / materials / equipment / samples / containers / tables / steps / controls / expectedOutputs / troubleshooting / safety / biosafetyLevel / limitations / sources / provenance`.
- Immutable published versions, content-addressed by **`contentHash`**; edits create a new version.
- Lineage: **`parentVersionId`** (version chain) + **`derivedFromVersionId`** (fork/submission edge).
- Three libraries (public / private / lab) with **RBAC** (`LabMembership` roles viewer/editor/reviewer/owner).
- A **full review state machine** (`draft → submitted → approved | changes_requested`) with an immutable `Review` audit trail, reviewer identity, and approval bound to `{versionId, contentHash, reviewerId, timestamp}`.
- **`Run`** bound to an exact `protocolVersionId` with an immutable body snapshot.
- **"A newer version exists"** banner already specified (Section 3 §4).
- A **`license`** field that travels with the body (`sources[].license`, `licenseVerified`; preserved on fork/tombstone).
- Tombstone archival (no hard delete of referenced versions) and a validator (`renderer/validate.mjs`) on every write path.

Ideas are ranked by leverage on top of that baseline. Each carries a **how-we-adapt-distinctively** note and an **already-have / v0.2+** tag. Several draft "v0.2+" items turned out to be *already-have* once checked against the real schema — those are corrected below.

**1. Protocol↔run duality with an auto-named, version-pinned, *typed* execution record.** — Labstep auto-creates a dated run from a protocol ([Labstep](https://help.labstep.com/en/articles/5493023-using-protocols-on-labstep)); eLabFTW duplicate-template→dated "Running" experiment ([eLabFTW](https://doc.elabftw.net/docs/usage/user-guide/experiments/)); protocols.io Run mode ([run](https://www.protocols.io/help/ongoing-research-work/run)). *Why:* cleanly separates the reusable template from the immutable execution instance. *How we adapt distinctively:* our `Run` already snapshots + pins `protocolVersionId`; extend the snapshot with a per-step **actuals** array that fills only the typed-parameter slots the protocol already declares — so a run is a *typed diff against a hashed template*, not a free-form notebook page. Auto-title from metadata + timestamp, binding stays machine-checkable via `contentHash`. *Status:* run-bound-to-version and snapshot **already have**; auto-named typed run record + per-step typed actuals = **v0.2+**.

**2. Lockable template steps so a run fills results but cannot silently rewrite the method.** — eLabFTW read-only template steps ([eLabFTW](https://doc.elabftw.net/docs/usage/user-guide/experiments/)). *Why:* the integrity boundary between "the method" and "what happened." *How we adapt distinctively:* our versions are already immutable + hashed, so a run cannot alter the method by construction; we go further by marking each step field `locked` vs `runFillable` in the schema, so a genuine deviation becomes an explicit, typed **`deviation`** entry attached to the run (with reason), never an edit. *Status:* immutability **already have**; `locked`/`runFillable` flag + typed deviation record = **v0.2+**.

**3. Fork/derive with automatic provenance link + a *typed structural* diff.** — protocols.io fork-with-link and compare ([contribute](https://www.protocols.io/help/contribute)). *Why:* turns a static library into a traceable reuse graph. *How we adapt distinctively:* lineage (`derivedFromVersionId`) is **already have**; add a **structural diff over the canonical JSON** at step/parameter/material granularity (not a text diff), exploiting our typed schema so a fork shows exactly which parameters/materials changed. *Status:* lineage **already have**; typed structural diff/compare view = **v0.2+**.

**4. Input/output material tagging with a sample lineage graph.** — Labstep input-vs-output fields + parent→product lineage ([Labstep](https://help.labstep.com/en/articles/5493023-using-protocols-on-labstep)); eLabFTW `#` bidirectional experiment↔resource links ([eLabFTW](https://doc.elabftw.net/user-guide.html)). *Why:* material traceability and reproducibility become a byproduct of the data model. *How we adapt distinctively:* add a per-step `role: input | output | consumed` on `materials`/`samples`; when a run produces an output sample, record its parents so LabRecord renders a **sample lineage graph that composes with our existing protocol lineage** — protocol-provenance and material-provenance in one model. *Status:* `materials`/`samples`/`containers` exist; role tag + sample lineage = **v0.2+**.

**5. Typed step components auto-aggregating into a derived Materials view / shopping list.** — protocols.io gadgets auto-fill the Materials tab ([editor](https://www.protocols.io/help/editor)). *Why:* machine-readable steps enable scaling, auto shopping lists, and QC without re-typing. *How we adapt distinctively:* steps already carry typed parameters; add a **derived Materials view** computed from step parameters (dedupe reagents, sum amounts) and a **validator rule** asserting step-declared vs header-declared materials are consistent. *Status:* typed params + materials **already have**; aggregation + consistency check = **v0.2+**.

**6. A structured "Resources manifest" enforcing a source + persistent identifier on every referenced item.** — *inspired by* STAR Protocols' key-resources table ([resources table](https://www.elsevier.com/researcher/author/tools-and-resources/key-resources-table)); we do **not** adopt its name or column set. *Why:* forces every reagent/software/model/dataset to carry a source + persistent ID → clean reproducibility metadata + indexing. *How we adapt distinctively:* we already have `sources`; add a validator rule that every material/equipment/software/dataset referenced in a step **resolves to a `sources` entry carrying a persistent identifier** (RRID / cat# / DOI / URL), and expose a *generated* resources table from our own schema. *Status:* `sources` + validator **already have**; cross-link enforcement + generated table = **v0.2+**.

**7. Retract-and-supersede for corrections (never delete).** — Bika/SENAITE retraction that **preserves the original result** ([verify/retract](https://www.bikalims.org/manual/workflow/images-ar-verification/verify-or-retract-analysis-results-in-bika-and-senaite/view)). *Why:* handles "I entered a wrong value" without breaking the audit chain. *How we adapt distinctively:* for run records (which capture real data), a correction creates a **new run version referencing the retracted one via lineage** with a `retractedReason`; the original stays `contentHash`-addressable and tombstoned, not removed. Reuses our existing lineage + immutability + tombstone rather than a separate snapshot store. *Status:* lineage/immutability/tombstone **already have**; run-level retract-with-reason = **v0.2+** (once run records exist). *(This idea rests only on the bikalims.org primary manual; the draft's stronger "immutable before/after snapshot" claim was dropped as unverifiable.)*

**8. Scannable sample/inventory identifiers with quantity + stock decrement on use.** — Benchling registers samples by ID ([registry](https://help.benchling.com/hc/en-us/articles/39953982240397-Create-and-manage-entities-with-the-Registry)); SciNote/Labguru/RSpace/Quartzy key inventory on IDs with stock/quantity tracking ([SciNote](https://www.scinote.net/product/); [Labguru](https://help.labguru.com/en/articles/5832668-how-data-integrity-can-be-ensured-when-working-with-labguru); [RSpace](https://www.researchspace.com/inventory); [Quartzy](https://www.quartzy.com/tour/inventory)). *Why:* the draft covered material *lineage* but not identity/quantity — the piece that makes inventory usable at the bench. *How we adapt distinctively:* give `samples`/`containers` a stable `sampleId` (barcode/QR-encodable) and an optional `quantity`; when a run consumes a `role: consumed` material, decrement the referenced sample's quantity and record the debit against the run — inventory movement falls out of the same run-actuals model as everything else. *Status:* `samples`/`containers` exist; scannable IDs + quantity/decrement = **v0.2+**.

**9. Attach raw instrument/result files to a run (optionally parsed into typed slots).** — Benchling lab-automation parses instrument output files ([lab automation](https://docs.benchling.com/docs/use-apis-to-process-outputfile-with-lab-automation)); RSpace attaches files to ELN docs ([features](https://www.researchspace.com/features)). *Why:* runs currently capture typed actuals but have nowhere to hold the raw evidence (gel image, plate-reader CSV, chromatogram). *How we adapt distinctively:* add a typed `attachments[]` on the `Run` (fileRef + kind + optional `parsedInto` mapping to specific actuals slots), so raw files hang off the immutable run snapshot and, where a parser exists, populate typed actuals rather than living as opaque blobs. *Status:* runs store results; typed attachment model = **v0.2+**.

**10. `.eln` / RO-Crate interchange export alongside our JSON.** — eLabFTW and RSpace both export the standardized `.eln` archive (ZIP of metadata + `ro-crate-metadata.json`) ([eLabFTW](https://doc.elabftw.net/docs/usage/user-guide/experiments/); [RSpace](https://documentation.researchspace.com/l/en/article/s3j29if453-export-formats)). *Why:* adopting an existing open interchange standard makes LabRecord interoperable with the two biggest open ELNs and future-proofs export. *How we adapt distinctively:* keep our canonical JSON as source of truth; add a **mapper** that emits a valid `.eln`/RO-Crate wrapper — interop as an export target, not a schema change. This is the one item we conform to directly, because RO-Crate is an open spec meant to be implemented as-is. *Status:* JSON export **already have**; `.eln` mapper = **v0.2+**.

**11. E-signature + optional witness countersignature on approval.** — Benchling e-sign locks prior versions ([Benchling](https://help.benchling.com/hc/en-us/articles/10450761643917-Creating-entry-review-processes)); Labguru sign + witness routing ([Labguru](https://help.labguru.com/en/articles/5832668-how-data-integrity-can-be-ensured-when-working-with-labguru)); LabArchives e-sign → permanent page + witness countersign ([LabArchives](https://www.labarchives.com/blog/how-to-choose-the-best-electronic-lab-notebook-software)). *Why:* a proven, Part 11-aligned trust model. *How we adapt distinctively:* the **review state machine, reviewer identity, and tamper-evident `{versionId, contentHash, reviewerId, timestamp}` binding already exist** — so unlike the draft (which treated this as building a review workflow), the remaining delta is only the *signature semantics*: an explicit e-sign action and an optional second **witness** countersignature, both anchored on the existing `contentHash` rather than a new audit subsystem. *Status:* review workflow + reviewer-in-provenance **already have**; e-sign + witness countersign = **v0.2+** (small delta). *(The draft's LabArchives "data-layer audit cannot be disabled" claim was dropped — it rested on a non-primary SEO blog.)*

**12. Faceted / full-text search and cross-library discovery.** — eLabFTW full-text + filters by category/tags/archived/deleted ([eLabFTW](https://doc.elabftw.net/docs/usage/user-guide/experiments/)). *Why:* almost every "Search" cell in §1 is `?`, and discovery is a core platform pattern the draft never addressed. *How we adapt distinctively:* index the typed canonical JSON so search facets are *structural* (by material/equipment identifier, biosafety level, category, license, library scope) on top of full-text — richer than free-text ELN search because our fields are typed. *Status:* not present; search/discovery layer = **v0.2+**.

**13. ## 3. IP / anti-plagiarism

General data-management *concepts* are free to be inspired by — nobody owns "immutable versions," "fork with provenance," "run mode," "input/output material lineage," "review-and-sign," or "typed reagent tables." These are industry patterns, and several sources here are explicitly open (protocols.io content is **typically CC-BY but the license is author-selectable per protocol**, so it is not blanket-CC-BY; eLabFTW is AGPL open source; SENAITE/Bika are open source; the `.eln`/RO-Crate format is an open standard). We may adopt the *ideas* and cite where each originated.

We must **NOT**:

- **Copy protocol text, datasets, figures, or example content** from any platform or journal into LabRecord (protocols.io content, even where CC-BY, still requires attribution and cannot be passed off as ours; journal protocol text from Nature/Cell/Wiley/Bio-protocol/JoVE is copyrighted).
- **Copy verbatim schemas or field-name/vocabulary sets** — do not reproduce Benchling's schema/fieldset definitions, STAR's key-resources-table column set, protocols.io's gadget field layouts, eLabFTW's role names, Nature Protocols' section order, or Current Protocols' "Basic/Alternate/Support" role names as-is. The field-name strings quoted in §1 are cited descriptions of prior art, **not** adoptable vocabularies. We reimplement independently on our own canonical JSON with our own field names.
- **Copy UI copy, layout, iconography, help-text wording, or workflow labels** verbatim — e.g. do not ship the literal string "Run of [Protocol name]", "Key Resources Table" as a product artifact name, or another product's button/label text.
- **Use branding or trademarks** — names/logos (protocols.io, Benchling, eLabFTW, Labstep, STAR Protocols, Current Protocols, etc.) must not appear as if endorsing or affiliated with LabRecord.
- **Copy source code** from open-source projects (eLabFTW/AGPL, SENAITE) into our codebase — AGPL/GPL terms would attach obligations; we reimplement from documented behavior, not from their code.

Practice: **reimplement every idea independently from the documented behavior, express it in our own schema/terminology, and record provenance** — keep a short "prior art / inspiration" note (idea → source URL) in our design docs so influence is transparent and attributable. For the one open interchange standard we adopt directly (`.eln`/RO-Crate), we conform to the public spec, which is its intended use.

**Key open decision (do not silently default):** *persistent citable identifiers for public protocols.* Every journal and protocols.io mints a DOI so protocols are citable; LabRecord's public library currently relies on internal `versionId` + `contentHash`. This is a genuine platform-pattern gap, so it should be a **recorded decision with tradeoffs**, not an omission:
- *Option A — internal-only IDs:* zero external dependency; `contentHash` already gives an immutable, verifiable handle. Cost: protocols are not citable in the scholarly graph and won't surface in CrossRef/DataCite.
- *Option B — mint DOIs (e.g. via DataCite) per public version:* real citability + discoverability; cost is a registration dependency, fees, and a commitment to permanence.
- *Recommendation:* keep `contentHash` as the internal anchor now; treat DOI minting as an explicit later decision gated on whether the public library is meant to be citable. Pair this with the **per-protocol author-selectable `license`** we already store — on public submission the author selects the license, and **attribution must propagate on fork** (Section 3 §7 already carries `license` down lineage; the remaining work is surfacing license choice at submit-time and attribution in the UI).
